Context of Business

Currently, all users with enquiry access see the same pool of applications regardless of team boundaries. This enhancement introduces two capabilities:

  1. Staff ID & Case Attribution: Each bank portal user is assigned a Staff ID that links them to applications originating from the Distribution Portal (via UTM staff_id, the Referral Code pop-up or round-robin assignment). This provides the matching key for visibility filtering. Staff ID is the bank’s existing staff identifier (Sales Code, Agent Code or Employee ID), accepted as free text. Staff ID and Reporting Manager apply to users with Department = Sale only.
  2. Reporting Manager Hierarchy & Visibility Filtering: A Reporting Manager field on the user record establishes a reporting chain. Staff-level users see only applications tagged to their Staff ID. Manager-level users see applications tagged to all users in their reporting subtree (unlimited depth). Visibility filtering applies only to users with Department = Sale. Users in any other department see all applications, subject to their existing role permission to view Application Enquiry and Report Enquiry.

These rules apply across Application Enquiry and Report Enquiry as pre-filters before all existing filters.

Department Rule (Department = Sale)

Department = Sale drives this enhancement:

  1. Staff ID and Reporting Manager are shown on Add User / Edit User only when [Department] = Sale.
  2. The visibility filter (AC5/AC6) applies only to users with Department = Sale.
  3. Users in all other departments see all applications, provided their role has the View permission for Application Enquiry / Report Enquiry (existing Role Management permissions, no new permission).

User Story

As a bank portal administrator,
I want to assign a Staff ID and Reporting Manager to each user so the system can tag applications to staff and restrict enquiry screen visibility based on the reporting hierarchy,
So that staff members see only their own assigned cases, managers see their reporting subtree’s cases, and operations/admin users retain full visibility across Application Enquiry and Report Enquiry.

AC4. Case Attribution — How Applications Get Tagged to Staff

For the visibility rules in AC5–AC6 to function, each application must be tagged with a Staff ID identifying the assigned staff member. Attribution occurs through two mechanisms with the following precedenceis resolved at submission from the codes captured in the journey:

  • If the application URL contains a salesagentCodestaff_id parameter, only UTM attribution (mechanism 1) is attempted. If the code matches an active Staff ID, the application is tagged. If the code does not match (typo, staff left), the application remains untagged — round-robin is not evaluated as a fallback.
  • If the application URL contains no salesagentCodestaff_id parameter, round-robin (mechanism 2) is evaluated to auto-assign the application to a staff member.
  • Mechanism 1 — UTM: staff_id parameter of the link. Mechanism 2 — Pop-up: Staff ID entered in the Referral Code pop-up ( AMP-464 UAT Validated ). Both optional; each capture is audited with source and timestamp.
  • Latest captured value matching an active Sale-department Staff ID (canonical key) wins.
  • No matching value (no code, typo, inactive user): sales round-robin (mechanism 3) runs if a pool is configured for the channel/product; otherwise the application remains untagged. Unmatched raw value kept; ET51 alert to queue/ops admin.
Mechanism How It Works Reference
1. UTM Attribution (first priority)
  • When a customer applies via a Distribution Portal UTM link containing a staff_id parameter, the system captures the code and performs a match on the canonical key (case- and separator-insensitive) against all active bank portal users’ Staff IDs
  • If a match is found, the application is tagged with that user’s Staff ID at originationsubmission
  • Unmatched code: If the staff_id does not match any active Staff ID (typo, staff left the bank, or code never assigned), the application remains untagged. The system does not fall back to round-robin for unmatched codes. is treated as untagged and goes to sales round-robin (mechanism 3) where a pool is configured. An alert email (ET51 pattern) is sent to the queue/ops admin listing the unmatched code, application reference, and origination timestamp so the mismatch can be investigated
 AMP-3323 (UTM ID in generated URL)
2. Referral Code pop-up
  • Shown when the channel referral flag is on ( AMP-464 UAT Validated baseline); the customer enters the Staff ID given by the salesperson.
  • Validated live against active Sale-department Staff IDs (canonical key). Unknown value: “Code not recognised — check with your salesperson or continue without”.
  • AC1 format rule applied server-side. Stored as raw value + resolved Staff ID + source = Pop-up.
 AMP-464 UAT Validated , AMP-1454 UAT Validated
2.3. Sales Round-Robin Auto-Assign (second priority)(untagged cases only)
  • Trigger: At origination, when the application URL contains no salesagentCodestaff_id parameter (i.e., UTM attribution was not attempted) At submission, when no captured code matches an active Staff ID and a pool is configured for the channel/product.
  • Eligible pool: Active users with Department = Sale who have a Staff ID assigned, configurable per channel and product type. Only users with a Staff ID are eligible — users without a Staff ID are excluded from the pool (their cases would be invisible to them under AC5/AC6 visibility rules)
  • Selection algorithm (same mechanics as ACP-18 AC1, applied to the sales pool): scan the eligible pool → select the user with the lowest attributed application count → break ties alphabetically by email
  • Output: The selected user’s Staff ID is written as the application’s attribution. This is a sales attribution, distinct from the queue’s “Assigned To” which is set separately when the application enters a processing queue
  • If no eligible assignee is found (pool empty or not configured for this channel/product), the application remains untagged and an alert email (ET51 pattern) is sent to the queue/ops admin
 ACP-18 AC1 (algorithm precedent only — trigger, pool, and output differ)
  • Unattributed applications: If neither mechanism produces a tag (unmatched UTM code, or no matching code and round-robin pool empty / not configured), the application remains untagged. Untagged applications are visible to users in non-Sale departments only. Not every application carries a Staff ID: both codes are optional.
  • Attribution is immutable after originationsubmission. The Staff ID tag set at origination does not change, even if the tagged user’s Staff ID is later corrected by creating a new user record (Staff ID is read-only once set per AC1). No reassignment function: the tag never changes, including on user deactivation or when a replacement user record is created.
  • The application stores the raw entered value, the resolved Staff ID and the source (UTM / Pop-up / Round-robin / Backfill).

AC5. Staff Visibility — Own Assigned Applications Only

Mockup: Tab “Hierarchy & Visibility” — see the Case Visibility Comparison section showing which applications each user role can see.

A user with Department = Sale sees only applications tagged to their Staff ID and to their reporting subtree (AC6). This filter applies as a pre-filter before all existing filters (channel, product type, status, search) on every enquiry screen listed in AC9.

  • The system matches the logged-in user’s Staff ID against the application’s attributed Staff ID (set via AC4).
  • Applications tagged to other staff are excluded from the list.
  • If no applications are tagged to the user, the screen displays IM005 “No results found.”
  • The department pre-filter is the only additional restriction: no implicit date window, default filters identical to other users.

AC6. Manager Visibility — Full Reporting Subtree (Unlimited Depth)

Mockup: Tab “Hierarchy & Visibility” — see the Organisation Chart showing the reporting subtree traversal and Fatima’s / Khalid’s visibility examples.

A Sale-department manager sees applications tagged to all users in their reporting subtree, with no depth limit. This filter applies as a pre-filter before all existing filters on every enquiry screen listed in AC9.

  • The system traverses the reporting chain downward from the logged-in user recursively with unlimited depth: collects all users whose Reporting Manager =s include the logged-in user (level 1), then all users whose Reporting Manager is one of those users (level 2), and so on until no more reports are found. A user with several managers appears in each manager’s subtree; an application is listed once.
  • The screen displays all applications where the attributed Staff ID matches any user in the subtree, plus the manager’s own tagged applications.
  • If the manager has no reports and no own tagged applications, the screen displays IM005 “No results found.”

AC7. “View All Applications” Permission — Removed

Removed. Replaced by the department rule: users with Department ≠ Sale see all applications, including untagged ones, through their existing View permission for Application Enquiry / Report Enquiry. No new permission is created.

AC8. Reporting Manager Lifecycle Rules

Edge cases for managing the Reporting Manager field over time.

Scenario System Behaviour
Circular chain prevention
  • If assigning User A as the Reporting Manager of User B would create a cycle at any depth across any manager edge (e.g., A → B → C → A), the system blocks the save and displays IEM002 “This assignment would create a circular reporting chain.”
  • Self-assignment (User A as their own RM) is a special case of this rule and is also blocked.
Deactivating / deleting a manager with reports
  • If a user who is the Reporting Manager for one or more active users is deactivated or deleted, the system displays IEM003 “This user is the Reporting Manager for [N] active user(s). Reassign their reports before deactivating.”
  • The deactivation/deletion is blocked until all direct reports are reassigned to another Reporting Manager or set to None.
Deactivating a staff user with tagged applications
  • If a user with a Staff ID who has open tagged applications (applications attributed to their Staff ID that are not in a terminal status) is deactivated, the system displays IEM004 “This user has [N] open tagged application(s). Reassign their cases before deactivating.”
  • The deactivation is blocked until all open tagged applications are reassigned to another staff member or reach a terminal status.
  • Deactivation is allowed. Open applications keep the Staff ID tag and remain visible to the user’s Reporting Manager(s) and to non-Sale users. IEM004 removed.
Mid-flight RM change — visibility is real-time
  • When a user’s Reporting Manager is changed (after Checker approval), the visibility recalculation takes effect immediately.
  • The new manager’s subtree now includes this user and their applications. The old manager’s subtree no longer includes them.
  • Existing applications tagged to the user move with them — visibility follows the current hierarchy, not the hierarchy at the time of application creation.
  • Rules apply per manager edge: adding or removing a manager updates that manager’s subtree in real time.
Department changed to Sale
  • Staff ID becomes mandatory: the Staff ID and Reporting Manager fields appear on selecting Sale and the save is blocked until a Staff ID is entered.
Department changed from Sale to another department
  • Blocked while the user is Reporting Manager of active Sale users (IEM003) or has open tagged applications (IEM004).
  • Otherwise Reporting Manager is cleared to None, Staff ID is retained read-only and hidden so historical attribution stays resolvable, and the user sees all applications per their enquiry permissions from the next request.
Scope evaluation
  • Visibility scope (Department, Staff ID, reporting subtree) is evaluated server-side from the user record on every request, never cached in the login session.

AC10. Saving Rules & Maker/Checker Request

Mockup: Tab “Maker/Checker Request” — see the Maker Queue list screen, the Checker Detail screen with old/new comparison, and all request type scenarios.

  1. The Staff ID and Reporting Manager fields are saved as part of the user record when the administrator clicks “Save” (Add User) or “Save Changes” (Edit User).
  2. Both fields follow the standard Maker/Checker flow (ACP-245). A request is created in Maker Queue and routed to Checker Queue per ACP-250 authority matching. Changes take effect only after Checker approval.
  3. Staff ID uniqueness validation runs at save time (before Maker request creation). If a duplicate is found, the save is blocked and the request is not created. Staff ID format (IEM005) and the mandatory rule for Department = Sale are validated at the same point and again at Checker approval.
  4. Circular chain validation (AC8) runs at save time. If a cycle is detected, the save is blocked.
  5. Checker-time re-validation: The system re-runs Staff ID uniqueness and circular chain validation at Checker approval time (not only at save time). Two concurrent Maker requests may both pass save-time validation but conflict at approval. If the Checker approves request B and Staff ID uniqueness or circular chain validation fails (because request A was approved first), the system blocks the approval and displays the relevant error (IEM001 or IEM002). The Checker must reject the request, and the Maker must re-submit with corrected values.

Impact Analysis

IA1. Maker/Checker Queue — Not Affected

  • Maker/Checker Queue (ACP-245/248/250) handles admin configuration requests, not application processing. The visibility rules do not change Maker/Checker routing. Existing authority set and approval level rules remain unchanged.

IA2. Unassigned & Historical Cases

  • Pre-existing applications: All applications created before this enhancement have no Staff ID attribution. These applications are visible to non-Sale users only.
  • Migration strategy (decided): (a) Non-Sale departments: no change. (b) Existing users with Department = Sale: Staff ID must be assigned via Edit User (Maker/Checker) at go-live; until then the user sees no applications (IM005). (c) One-off backfill: historical applications whose stored [Referral code] ( AMP-464 UAT Validated / AMP-1454 UAT Validated ) matches an active Staff ID canonical key are tagged to that Staff ID (source = Backfill, audited). Other historical cases remain visible to non-Sale users only. No round-robin backfill.
  • Round-robin for ongoing applications: Applications with no UTMmatching attribution are auto-assigned via the sales round-robin mechanism defined in AC4 mechanism 23, where a pool is configured. The sales round-robin uses the same selection algorithm as ACP-18 AC1 (lowest count → alphabetical tiebreak) but with a different trigger (at origination, not at queue entry), a different pool (active users with Department = Sale and with a Staff ID, per channel/product), and a different output (Staff ID attribution, not queue Assigned To). No separate ticket is required — the mechanism is fully defined in AC4.

IA3. Email Notifications

  • If existing email notifications are sent to the assigned staff member (e.g., case assignment, status change, document upload), evaluate whether the Reporting Manager should be CC’d on these notifications.
  • This requires an audit of all notification templates that reference the assigned user. If CC is needed, a separate enhancement ticket should define which notification types include the Reporting Manager.

IA4. UTM Integration (Distribution Portal)

  • AMP-3323 (UAT Validated) defines the UTM ownership model in the Distribution Portal. AMP-3323 UAT Validated carries no agent code (utm_id / source / medium / campaign only). Staff ID is added as an optional UTM parameter staff_id via the Super Admin-configurable parameter list (IH14 §1.2.1), one name across all channels and products, stored on the application under IH14 §3.4. The Staff ID field in this story provides the Bank Portal side of the link.
  • The Distribution Portal captures staff_id from the UTM URL and stores it with the application. The Bank Portal matches this code ( canonical key: uppercase, separators removed) to a user’s Staff ID for visibility filtering.
  • Permission separation: AMP-3323’s “View All Application Sources” is a Distribution Portal permission that bypasses UTM ownership filters. This story creates no Bank Portal permission; visibility follows the department rule.
