Step 2 Round-robin default — configurable rotation ADIB-7172
Config table drives the rotation — DB-configurable, no hardcoding:
· IFE_CODE — the staff referral code
· SEQUENCE_ORDER — pick order
· LAST_ASSIGNED_FLAG — where the wheel stopped
· IS_ACTIVE — enable/disable without deletion

Strict sequence: next active code in order, loop back after the last. A newly added code is prioritized once, then the sequence resumes.
Rotation example (5 applications, 3 active codes):
App 1 → IFE-001→ App 2 → IFE-002→ App 3 → IFE-003↺ App 4 → IFE-001→ App 5 → IFE-002

3 · Alignment check — ADIB logic vs AMP-2548 v4

DimensionADIB logicAMP-2548 v4VerdictAssessment
Attribution key Staff code carried in UTM salesagentCode; person-level Same — Staff ID mapped to salesagentCode Aligned Adopted directly from the ADIB-6725 pattern, as recommended.
Capture channels 4: UTM + QR + manual + round-robin 2: UTM + round-robin (QR/manual dropped for phase 1) Deviation Deliberate scope cut — no SMBP journey screen exists for QR/manual yet. Aligned in principle; revisit in phase 2.
Precedence Latest successful code wins across channels; every attempt logged in a Referral table First wins — single evaluation at origination; no attempt log (final tag + alert only) Deviation Acceptable for phase 1: with only UTM + fallback there is no second capture event. Must be revisited when QR/manual returns — then ADIB's latest-wins + attempt logging is the proven rule.
Tagging guarantee Every application ALWAYS tagged (DSA mandatory; codes stored as-is, no user matching needed) Untagged allowed: unmatched code or empty pool → View-All only + ET51-style alert Deviation Justified by the different purpose: ADIB's code is pass-through attribution to FinnOne; SMBP's tag grants visibility, so a bad code must not silently assign visibility. The alert closes the operational gap.
Round-robin algorithm Strict sequence rotation (SEQUENCE_ORDER + LAST_ASSIGNED_FLAG; new code prioritized once) Load-based: lowest attributed count, A→Z tiebreak (ACP-18 mechanics) Deviation Different fairness model — rotation gives equal turns, load-based balances volume. Both distribute; confirm with the bank which model sales management expects, then state the choice once in AC4.
Round-robin config DB config table, active flag, no hardcoding Pool configurable per channel + product type, active + Staff ID only Aligned Same principle. One open detail: WHERE the pool is configured (screen? maker/checker?) is not yet specified — add to AC4 or a config story.

Reporting Staff referral report from Application table Report Enquiry scoped by the same tag (AC9) Aligned Same data point drives both.
Correction / lifecycle Code finalized at submission; no reassignment concept needed (attribution only) Immutable tag + IEM004 demands reassignment before staff deactivation — but no reassignment function exists Open — P1-B Not an ADIB alignment issue — an internal contradiction still open in v4. The Round-3 comment as posted carried only P1-A, so the BA has not seen this yet. One fix: add a "Reassign Case (Sale Staff)" function (permission-gated, maker/checker, audited) and reword AC4 immutability to "changes only via explicit reassignment."
Verdict: AMP-2548 v4 follows the ADIB spine — person-level staff code, UTM as carrier, configurable round-robin default, audit + portal display + reporting on the same tag. The four deviations are deliberate and defensible (phase-1 scope, visibility-driven untagged rule, load-based selection) — confirm the round-robin fairness model with the bank. One blocker before approval: P1-B — the reassignment function IEM004 depends on does not exist yet.
