Section BFindings — ordered by severity (P1 first)

F1 P1 The stories drop the settle step (CF 1.3) that the design page and the screen copy still contain — the flow is undefined between MATCH and CF 1.18

What is wrong
Confluence 2122317829 decides D1/D2: "CF 1.16 is called WITHOUT ENQ DE 2 … the onboarding is settled in a separate step via CF 1.3" and PP-08 triggers on "PP-06 settle completed (result code 1 or 2)". AMP-3710 (Context, AC5.11, IA1) says "on MATCH … proceeds directly to CF 1.18"; its journey table has no PP-06; AMP-3711's pre-condition is "CF 1.16 … result code 1 (MATCH)" with no settlement. The bilingual copy posted in the comments still has "PP-06 — Account Settled: Account Created / Account ID" and PP-05 "Check 3: Account ID generated". Three documents, three flows.
Why it matters
In the EID journey, 1.2 is called with the Account ID and the identity is settled in the same call (761954749 Part B; AMP-2651 now generates the 9-digit ID for it). Per PP-06 on the design page, after a 1.16 MATCH the onboarding "is held in EFR's temporary store under the intermediary GUID" until CF 1.3. Without settling, no Rightful Holder account exists for the passport applicant: IC1.1 (income, IB-348) and the account-level CF 1.19 have nothing to key on, and the temporary GUID has a lifetime nobody has written down. "1.16 = 1.2" is only true if the identity ends up settled.
What to update
Take decision D1 (Section C). If D1 = settle: add AC5.12 "Generate Account ID and settle via CF 1.3" to AMP-3710 (or a linked story) using the AMP-2651 generator, set AMP-3711 pre-condition to "settle completed with result 1 or 2", and align AC5.11 / IA1 / the journey table / PP-05 and PP-06 screen copy. If D1 = no settle: write that decision into both stories with the EFR confirmation that the GUID stays valid for 1.18 and what its expiry is, and remove PP-06 and "Account ID generated" from the screen copy.

F2 P1 Three application-status vocabularies for the same outcomes, and a new attribute "EFR Sub-Reason" that exists nowhere

What is wrong
AMP-3710 uses Declined / Cancelled / In Progress + "EFR Sub-Reason" (Routed_to_EID, Existing_Customer, Failed_by_EFR, EFR_Scan_Exhausted, EFR_Timeout …). AMP-3711 uses Cancelled for every failure and Awaiting Credit Approval on success. The design page uses Referred, Insufficient Data, Routed_to_EID, Existing_Customer, Failed_by_EFR as the Application Status itself. The baseline status list (1.5.4) knows Lead, In-progress, Awaiting Compliance Review, Awaiting Credit Approval, Rejected, Blocked, Expired, Approval in Principle …; "Declined" appears only in the EFR 1.2 saving rule on 761954749; "Cancelled" and "Referred" appear in neither.
Why it matters
Funnel reporting (AMP-3710 IA2), the manual-review routing (F3) and the Bank Portal enquiry all filter on status. A sub-reason that is not a field cannot be reported, shown or audited. The BA's own rule "Routed_to_EID must not be counted as a decline" cannot be implemented without knowing which column carries it.
What to update
One status table for both stories, every value taken from 1.5.4 (add rows there for the passport steps). Define [EFR Sub-Reason] as an attribute of {Application Detail}: value list, where it is set, shown in Application Enquiry and in the audit-trail [Step Detail]. Decision D5.

F3 P1 "Route to manual review" and HTTP 403 have no destination; AMP-3711 AC5.2 contradicts itself

What is wrong
AMP-3711 AC5.2: "Do not terminate the journey on HTTP 403. Log the forbidden reason and cancel automatically" — cancel is termination for the customer. The design page says "route to manual review" for the same case. AC3.3: "Any field code = 0 (NO MATCH): route to manual review with the mismatched fields flagged" — no queue, no status, no persona, no screen for the customer who is mid-journey. The same fraud signal (used portrait image) is "Terminate, flag for review" in AMP-3710 AC5.5 code 303 and "Cancelled" with no flag in AMP-3711 AC5.2 code -3.
Why it matters
The EID baseline is explicit: 1.12 403 codes are Failed (1.5.7 1.12_403.x), IC1.1 403 continues the journey with WPS = 0 (IB-348 AC3). "Manual review" has two real queues in 1.5.4 (Compliance Queue = Awaiting Compliance Review; Credit Queue = Awaiting Credit Approval). A NO MATCH on date of birth is a compliance question, not a credit one.
What to update
For each of: any field NO MATCH, any field NO RECORD, 403 code 0 / -1 / -2 / -3 / -4 — state status, queue, what the customer sees next, and whether the journey continues (as IC1.1 does) or stops. Remove "cancel automatically" from AC5.2 or remove "do not terminate"; they cannot both stand. Make code 303 (3710) and code -3 (3711) behave the same.

F5 P1 "Upload Passport" is not the same scanning: it is modelled as a third identity document type, never reaches the AC2 trigger, and has no OCR path

What is wrong
AC1 saves [Identity Document Type] = the selected option, and the third option is "Upload Passport". AC2 triggers only when [Identity Document Type] = "Passport", so an upload applicant never enters AC2. AC3 runs OCR "when [EFR scan] = ON and the user scans a passport" via the EFR SDK camera flow; no AC says what produces mrz, documentNumber, outputImages.front from a gallery JPEG. The design page PP-01 has two options, not three. RF-186 / RF-6 / RF-16 have no upload path — the EID scan is live SDK capture only.
Why it matters
A gallery image is a tamper vector the EID flow deliberately does not accept (screen photo, edited image); the only defence is MRZ check-digit validation, which is not specified anywhere. Blur / glare "SDK-level check" (AC2.1b row 4) names no SDK.
What to update
Decision D2. If upload stays: make it a capture method inside "Passport" (AC2 method 2 already says so — AC1 must not save it as a document type), name the engine that OCRs an uploaded image and returns the same envelope as AC3.1, add MRZ check-digit validation and the fraud rule, and count it in the same 5-attempt limit. If not: remove option 3, AC2.1b, the upload copy and the upload error table from Release 1 and keep the RF-186 scanning as asked.

F6 P2 Service error and timeout exhaustion cancel the application — a technical fault becomes a customer-terminal outcome

What is wrong
AMP-3710 AC5.7 / AC5.8 and AMP-3711 AC5.4 / AC6 / AC7: after 5 retries on 5xx or timeout → [Application Status] = Cancelled. The design page (PP-05 AC2.3) says "400 and 5xx are recoverable and must not produce an adverse decision against the customer" and routes exhaustion to Insufficient Data + manual review; the story deleted that sentence. 1.5.4 has the Transaction Posting Queue for exactly this: "if there is an Exception issue / System issue with 3rd parties … applications can be placed in this queue", with the Retrigger pattern (1.5.7 codes 1100–1102). AMP-3711 AC5.1 also says a 400 at CF 1.18 leads to "re-scan or re-capture" — PP-08 is a backend step with no screen and the 400 can come from declared contact / professional data that no scan will fix.
What to update
Decision D4. Exhaustion on 5xx / timeout → Step Status Exceptional Case, application to Transaction Posting Queue with retrigger, status unchanged; no notification to the customer that the application is cancelled. For 400 at 1.18: per error field, either correct the declared field (screen) or route to review; re-scan only for passport-field errors.
