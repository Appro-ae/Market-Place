1BUSINESS CONTEXT & CLIENT CASES
Salary-transfer pricing needs the salary at Reem Bank. Today the journey knows only NSTL — detected salaries, future transfers and clients without an account all fall out. The backend now classifies every applicant before the screen renders and asks only what it cannot derive.
C1

New to bank

Toggle ON → FSTL · asks the 1st salary credit date · CIF + account + IBAN created at fulfilment

C2

Salary already credits to Reem (detected)

Toggle stays visible, relabelled · asks nothing · releases at creation — no letter, no hold

C3

Has an account — salary elsewhere

Toggle ON → FSTL · asks the date · existing account reused, letter carries its IBAN

C4

Reem client without an account

Toggle ON → FSTL · asks the date · account created along the way — previously a dead end

Design anchor: a parallel application invalidates the one in progress — so the customer is never sent out of the journey to open an account first. NSTL (toggle OFF) keeps today's flow untouched.

4BACKEND LOGIC UPDATES
  • Classification before render: own-account salary credit in T / T-1 (primary), bureau IBAN match (confirmatory), products list for has-account.
  • Order rule: account + IBAN exist before the loan/card — settlement fields and the letter need them; one core call returns both.
  • Release condition: letter validated and first salary credit detected by the account-transactions watcher — never one alone.
  • Repayment: STL/FSTL by standing instruction from the Reem account — no DDA; NSTL keeps the DDA.
  • No IBAN question on FSTL/STL; grace is derived and adjusted once, on the offer.
