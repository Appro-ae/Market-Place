COMMERCIAL POSITION
The approved CR covers the current scope only, as described in the BRD: the ten agreed Push IDs for Credit Card, Personal Loan and CASA, in English and Arabic, on iOS and Android, the deep link into the Appro journey, the automatic retry when the Push API call fails, and regression testing.
• The original scope of work covers Email and SMS only. Updates to Email and SMS for new features are already part of the product.
• Push notification is new and bank-specific, so it is delivered as a product customisation. To fit the timeline, the scope is kept to an MVP that gets the feature live — for example, push content is not managed in Super Portal in this phase.
• The design is scalable, so the feature can be upgraded on top of this customisation after release.
Of note, moving forwards, the Bank does not need to worry about the CR concept anymore. Starting from October, Reem Bank moves to our dedicated development team model. The Bank approves one man-day package a year, and a dedicated squad works full-time for Reem Bank, backed by our specialists whenever needed. The Bank simply raises and signs off the requirement as today, and we start building right away, with no quotation and no waiting for budget approval, plus a monthly report on how many man-days have been used. For Push Notification, this means we go live on the agreed MVP scope, and the dedicated team can then pick up further enhancements based on real customer feedback, with no CR in the way. This is how we keep the solution future-proof, as you rightly highlighted.

RESPONSE TO MR. FADEL’S COMMENTS
1. Push notification configuration – avoid future CRs [MVP 1.1 scope · Later – dedicated team]
   In MVP 1.1 the content and the rules are fixed per Push ID, as agreed in the BRD (section 3); the retry parameters are backend settings. Any wording change before sign-off is simply incorporated. Business-managed configuration from Super Portal — enable / disable, content, reminder frequency and count, product mapping, validity, priority, English and Arabic, new Push IDs — is the next enhancement, picked up by the dedicated team after the MVP sign-off, with no CR.
   In BRD V1.2: A “Future enhancements” section listing these parameters; your requirement statement is carried there as the target design.

2. Complete end-to-end push notification journey [MVP 1.1 scope · Dependency – Avanza]
   On Appro’s side the journey is complete: each push is sent only at its trigger event on a live application, and the P02 reminder stops once the customer selects the offer or the application is expired, cancelled or rejected (BRD section 3). On tap, the Super App handles login and session, then opens the Appro journey at the screen for the event. Device-side cases — logged out, session expired, device changed, multiple devices, notification permission off, invalid token — sit with the Super App and the middleware; Avanza to confirm the behaviour and we will document it as received.
   In BRD V1.2: Extended flow and a scenario table with the owner of each case.

3. Deep-linking defined per notification [MVP 1.1 scope · Dependency – Avanza]
   Agreed — the destination screen per Push ID is part of the MVP scope, and BRD V1.2 will carry the table: Push ID, trigger, destination screen, and the screen when the application is no longer active (the application’s current status screen). Per the alignment call of 05/10, P03 and P09 carry action type NONE — the tap opens the Super App, with no deep link — and every other Push ID uses APPRO_JOURNEY. Logged in or logged out is the same from Appro’s side: the Super App completes the login, then hands over to the Appro journey, which opens at the destination screen. Avanza to confirm the hand-over keeps the destination after login.
   In BRD V1.2: Deep-link table for all Push IDs.

4. Reminder logic and suppression rules [MVP 1.1 scope · Later – dedicated team]
   P02 runs once per day for 15 days, as agreed. It stops immediately when the customer selects the offer, or when the application is completed, cancelled or withdrawn, rejected or expired — the full list goes into the BRD. The reminder interval and count are backend parameters in MVP 1.1; Business-managed configuration follows as an enhancement (item 1).
   In BRD V1.2: Reminder and stop rules stated explicitly.

5. Duplicate notification prevention [MVP 1.1 scope · Dependency – Avanza]
   One push per Push ID per trigger occurrence per application; a retry reuses the same request ID, so a system retry, timeout or reprocessing never creates a second notification on Appro’s side. Avanza to confirm the middleware de-duplicates on the request ID and accepts the same ID on retry (raised in section 4 of the BRD).
   In BRD V1.2: Business rule BR5 — one notification per event.

6. Arabic content before sign-off [Input – Reem Bank]
   English and Arabic are one requirement and are tested together in UAT. We have not yet received the approved Arabic titles and bodies. Please share them against the final English wording (item 7) and we will add them to the BRD before sign-off.
   In BRD V1.2: Arabic column in the content table.

7. Customer communication wording [MVP 1.1 scope · Input – Reem Bank]
   Accepted as proposed for P01, P04 and P09 — all within the 40 / 100 character limits and with no personal data on the lock screen. P05 depends on how the customer provides the document (Shurafa’s comment S6) and will be finalised with it. The full updated wording is in BRD V1.2 for your confirmation, so the Arabic can follow.
   In BRD V1.2: Updated content table.

8. Push timing and customer experience [MVP 1.1 scope · Later – dedicated team]
   Event-driven pushes are sent immediately. The scheduled ones — the P02 reminder and P03 (offer expired) — are sent at a fixed time of day, 10:00 UAE time. Configurable sending hours and customer local time are an enhancement for the dedicated team.
   In BRD V1.2: Timing rule per Push ID.

9. Audit trail and operational visibility [MVP 1.1 scope · Later – dedicated team · Dependency – Avanza]
   In MVP 1.1 each push is tracked in the backend against the application: Push ID, date and time, attempts, final status (sent / failed) and the failure reason. Until the Super Portal view is available, Appro support provides the status of a push for a given application on request from the Contact Centre. Showing it in Super Portal — an audit-trail entry or a notification report — is the next enhancement for the dedicated team. Delivery to the device, opened / clicked and deep-link success are Super App events that Appro does not receive; Avanza to confirm what the Super App can report.
   In BRD V1.2: Tracking fields listed; Super Portal view under “Future enhancements”.

10. Retry rules finalised [MVP 1.1 scope · Dependency – Avanza]
   Baseline values go into BRD V1.2: retry every 5 minutes, up to 3 attempts; a timeout counts as a failed attempt and is retried; the same request ID is reused on every retry; after the last attempt the push is recorded as failed and the application continues unaffected. Avanza’s error-code list arrived with specification v0.2 on 05/10; we propose 429, 500 and a timeout as retryable, and 403 and 404 as final with no retry — to be confirmed with Avanza.
   In BRD V1.2: Retry baseline values.
