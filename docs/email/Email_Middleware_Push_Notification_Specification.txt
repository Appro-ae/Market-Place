Dear Fahad,

Thank you for sharing the Push Notification specification v0.1 (25/09/2026). We have mapped it field by field to the Appro push notification flow. Most fields map directly. The points below need Avanza's confirmation before we can close the integration.

For each point we have put Appro's proposal — please confirm it or advise the correct value.

POINTS TO CONFIRM

CONNECTIVITY AND SECURITY
1. Endpoint — MW URL for SIT, UAT and PROD. The specification shows http:// — please confirm the endpoint is served over HTTPS.
   Appro proposal: HTTPS in all environments.
2. Authorization — How Appro obtains the Bearer token: token endpoint, grant type, expiry and refresh. Please also share UAT credentials.
   Appro proposal: Please advise.

HEADERS
3. stan — Format, length and uniqueness scope.
   Appro proposal: Generated by Appro, unique per request, including each retry.
4. channel_id — Value assigned to Appro, per environment.
   Appro proposal: Please assign.

REQUEST BODY
5. requestId — Format and length. On a retry, should Appro resend the same requestId so the middleware can de-duplicate?
   Appro proposal: Same requestId on every retry of the same push.
6. action — Behaviour of NONE, POPUP and APPRO_JOURNEY in the Super App, and how action.id and action.value are passed to the Appro SDK when the customer taps the notification. When does NA apply?
   Appro proposal: APPRO_JOURNEY for every push. action.id carries our Push ID (P01–P06, P08–P11). action.value is always CREDIT_CARD, PERSONAL_LOAN or CASA, so NA is not used.
7. recipient.mobilePhone — Format: country code, '+' sign, spaces? The sample value has a trailing space.
   Appro proposal: 971XXXXXXXXX — country code, digits only, no '+' or spaces.
8. recipient.customerId — NTB customers have no CIF. Is mobilePhone alone enough to reach them, and should customerId be omitted or sent empty?
   Appro proposal: Omitted for NTB.
9. recipient.email, content.message — Purpose of both fields, and where message is displayed versus body.
   Appro proposal: recipient.email: not sent. content.message: sent empty ("").
10. content.title, content.body — Maximum length supported by the Super App.
   Appro proposal: Title up to 40, body up to 100 characters.
11. content.language, timestamp — content.language is typed "Date Timestamp" — please confirm String, and the case ("en/ar" in the field list, "EN" in the sample). For timestamp, please confirm format and time zone.
   Appro proposal: language: String, lower case en / ar. timestamp: ISO 8601 UTC with milliseconds, as in the sample.

RESPONSE AND ERROR HANDLING
12. error.code — Full list of codes and messages, the HTTP statuses returned, and any code that should not be retried.
   Appro proposal: Success = HTTP 2xx with error.code "000". Anything else is retried up to the configured limit.
13. error.code "000" — Does "000" mean accepted for delivery, or delivered to the device?
   Appro proposal: Appro records "000" as sent, not delivered.
14. Timeout and volume — Recommended request timeout, and any rate limit. One of our pushes is a daily reminder, so volume can peak at the scheduled time.
   Appro proposal: Please advise.
