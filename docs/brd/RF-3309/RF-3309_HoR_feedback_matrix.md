| 1. Employer selection and validation — The Employer Name should not operate as an unrestricted free-text field wherever this can be avoided. The preferred design should allow the Credit user to search and select the employer from the approved Employer Master / Empaneled Company List. If free text amendment is required as an exception, the system should require additional validation before the updated employer can affect ALOC, DBR, income multiplier, eligibility or limit. Please also define the employer matching logic, including Such as Exact match, Fuzzy match / confidence threshold., Arabic and English employer names, Trade name versus legal name, Employer aliases, Duplicate employer records, Active/inactive employer status. The BRD currently states that the updated name will be matched against the Empaneled Company List and the classification rerun. This needs to be more explicitly controlled | Agreed. The design will be updated so the Credit user searches and selects the employer from the Empaneled Company List, with free-text entry kept only as an exception path. One point of clarity: the matching and classification logic is not new to this feature — it is the Day-1 platform logic (name matching against the Empaneled Company List at a 90% confidence threshold, company category and active status checks), and the edit simply re-runs it. We will document these matching rules explicitly in the BRD. Coverage of aliases, Arabic names and duplicates is a function of the Empaneled Company List data itself and is addressed under item 10. | Yes | BRD v1.1: employer search-and-select added to the edit section (screen SC3 updated); matching rules documented. Classification mechanics: no change — Day-1 logic, BRD v1.0 section 3. |
| 2. Source validation before applying the amendment — The employer amendment should follow a validation-first model. Where available, the amended employer should be validated against the relevant authoritative or supporting source, such as EFR / government employment record, salary information, employment certificate, pays lip or any other approved source used by the Bank. A manual amendment by the Credit user should not, by itself, be sufficient to establish a more favorable employer classification. | The design already works exactly this way. A name entered by the Credit user can never, by itself, establish a more favourable classification: the ALOC result is produced only by the system's independent match against the approved Empaneled Company List — if the corrected name does not match a listed, active employer, the application remains N-ALOC. This is the Day-1 classification model and this feature does not change it (BRD section 3; the match result including confidence score is displayed on screen SC5). Validation against EFR, salary records or employment documents is the Credit review that already takes place in the queue, where these documents are available to the user; an automated document-validation service is a separate initiative and not part of this change. | No change | Already covered — BRD v1.0 section 3 (system action 2), SC5. No system change required. |
| 3. Mandatory reason for change — Every Employer Name amendment must require a mandatory reason code. Suggested reasons: Spelling correction, Employer legal name / trade name correction, Employer alias, EFR / government record mismatch, Employer Master mapping issue, Customer-provided information correction & Other. (If Other is selected, a mandatory comment should be required) | We recommend keeping this edit consistent with the established Edit framework of the Credit Queue: none of the live edit functions (Finalized Income, Liability Information, Length of Service, Other Income and Expenses) captures a reason code, and the full old-to-new change, the user and the timestamp are already recorded in the Application History for every amendment (BRD section 3, screen SC6). Because the classification is system-derived (item 2), a reason code does not alter any decision outcome — it adds an input step to every correction. If the Bank sees value in reason codes, we suggest assessing it once, as a platform-wide convention across all Edit functions, rather than introducing it for this field alone. | Not incorporated | Traceability already covered — BRD v1.0 section 3 action 6, SC6. Reason-code convention: to be assessed as a platform-wide topic if prioritised. |
| 4. STP versus exception handling — Please define a clear STP decision matrix. The expected design should be: STP: Employer successfully matched and validated, no conflicting information and no exception criteria triggered -> automatically update the employer, rerun classification, recalculation, Rule Engine and routing. Controlled STP: Employer is validated, but the amendment creates a material positive credit impact -> system performs the recalculation automatically but applies the relevant Credit approval level / delegated authority. Exception: Employer cannot be confidently matched, evidence conflicts, repeated amendments are detected, or other risk conditions are triggered -> application should move to manual review rather than allowing an unrestricted override. | The STP leg described is precisely what this feature delivers: a successfully matched employer automatically triggers re-classification, recalculation, Rule Engine re-run and routing with no further manual step (BRD sections 3 and 6). Equally important, this edit is not an unattended process — it is performed by an authorised Credit user inside the Credit Queue, which is itself the Bank's manual-review control layer with its L1/L2/L3 structure; an unmatched name simply remains N-ALOC. A Controlled-STP / Exception decision matrix with delegated-authority routing is a credit-workflow design that goes beyond the capability this change delivers (edit the employer name and re-run the existing decisioning). We suggest taking it up as its own initiative where it can be designed across all queue actions, not only this field. | Not incorporated — new scope | STP behaviour: already in BRD v1.0 (flow + sections 3, 6). Decision matrix / delegated authority: proposed as a separate scope discussion. |
| 5. Material positive credit impact — The system must identify whenever the employer amendment creates a more favorable credit position, including where it: Changes N-ALOC to ALOC. Moves the employer into a more favorable category. Increases permitted DBR. Increases income multiplier. Increases approved/proposed limit. Removes a deviation. Converts an otherwise ineligible application into an eligible application. These cases should be specifically controlled and visible to the approving Credit user. | Visibility is already there: after the re-run the Credit user sees the re-classified ALOC with its match score, the employer category, the refreshed Rule Engine Result and the recalculated Approve Limit Result on the same screen (BRD section 4, screen SC5), and the before/after record in the Application History (SC6) — so every one of the listed movements is visible to the deciding user before any decision is taken. Automated detection of a favourable delta with approval gating belongs to the same decision-matrix design as item 4 and we propose handling both in that separate initiative. | Not incorporated — new scope | Visibility of all recalculated values: already covered — BRD v1.0 sections 3-4, SC5/SC6. Delta-detection control: with item 4 in the new scope. |
| 6. Repeat employer amendments — The current BRD states that there is no cap on repeat edits. Please revise this requirement. Unlimited employer amendments are not recommended where the employer classification directly impacts DBR, multiplier and limit assignment. The system should have a configurable control over repeat amendments. At minimum, any subsequent amendment after the initial correction should trigger additional authority, reason capture and appropriate monitoring. | Repeat amendments are already bounded and visible by design. Every amendment re-runs the Rule Engine under the platform's shared re-run counter — an application that fails the Rule Engine more than twice is automatically rejected — and every amendment writes its own fully detailed step in the Application History (BRD section 3, SC6), so repeated activity is immediately visible to anyone reviewing the case. The action is restricted to authorised Credit users inside the controlled queue environment. A configurable repeat-amendment threshold with escalating authority is workable, but it belongs to the same authority-matrix design as item 4; we propose deciding it there so the rule is consistent across all queue edits. | Not incorporated | Bounding and traceability already covered — BRD v1.0 section 3 (re-run counter, per-edit audit), SC6. Configurable threshold: with the item 4 scope discussion. |
| 7. Rule Engine rerun counter — Please ensure that: Technical/integration failures do not consume the business rerun counter. Only genuine business-rule failures are counted where appropriate. The customer is not rejected because of a system timeout, API failure or technical retry. | Confirmed — this is the existing behaviour. The counter counts business Rule Engine outcomes of the application; technical and integration failures are handled by the platform's error-handling and retry mechanisms and do not consume the counter or reject the customer. This is Day-1 platform behaviour that this feature re-uses unchanged; we will state it explicitly in the BRD for clarity. | No change | Existing platform behaviour — BRD v1.0 section 3 action 4; one clarification sentence added in v1.1. |
| 8. AML / KYC impact — The BRD currently states that AML screening will not be rerun following an employer amendment. Please reconfirm this treatment with Compliance and clearly document the agreed logic. If employer information forms part of customer risk assessment, KYC profiling or screening, the appropriate refresh/reassessment should be triggered. | The treatment is documented in the BRD (section 5) and is consistent with every existing edit function on the platform: screening is not re-triggered by a queue edit, and the corrected employer name reaches the screening system through the standard post-decision customer-update flow, so the screening record always carries the finalized value. We will take the action to put this in front of Compliance for confirmation; the documented logic stands unless Compliance directs otherwise. | No change | Documented in BRD v1.0 section 5. Action: Compliance confirmation — placeholder for the confirmation date added in v1.1. |
| 9. Fraud monitoring — Please include employer amendments in the fraud/control monitoring framework. Building fraud-monitoring views on top of that data is part of the Bank's control and reporting framework, which spans all portal activity — it is not specific to this feature and we propose planning it together with the reporting scope of item 18. | Not incorporated — separate stream | Monitoring source data: already covered — BRD v1.0 audit trail (section 3, SC6). Monitoring views: Bank reporting/control stream, with item 18. |
| 10. Employer Master governance — Please define the ownership and governance of the Employer Master / Empaneled Company List. Maker-checker for employer-master changes. | The Empaneled Company List is a Bank-owned master with its own established upload and maintenance process on the platform; its governance model, data dictionary and maker-checker controls are a standing capability question that applies to every function consuming the list, not only this one. We recommend raising it as a dedicated change request. This feature consumes the master as-is and will automatically benefit from any enrichment (aliases, Arabic names, employer IDs) made there. | Not incorporated — separate CR | Out of this feature. | 11. Source hierarchy — The BRD should clearly distinguish between Customer-declared Employer Name, Original system-derived Employer Name, Validated Employer Name and Credit-amended Employer Name. The original source should never be lost or overwritten. Please also define the source hierarchy so downstream users can clearly understand which employer information has been used for the final credit decision. | This distinction exists by design and is preserved by this feature. The customer-declared name (journey input) and the government-record sponsor name are never modified; the system-derived original is retained from the first amendment onward; the finalized value carries an explicit source attribute (government record / customer journey / Credit Department) with the amending user and timestamp; and it is the finalized value, alone, that drives the credit decision and every downstream consumer (BRD sections 3, 4 and 5; visible on screen SC5). We will add a one-glance hierarchy table to the BRD so this is readable in a single place. | No change | Already covered — BRD v1.0 sections 3/4/5, SC5. v1.1 adds a summary table only (presentation, not scope). |
| 12. Enhanced audit trail — Please expand it to capture at minimum Old Employer Name, New Employer Name, Old/new Employer ID, Old/new source, Old/new ALOC status/category, Old/new DBR, Old/new income multiplier, Old/new proposed/approved limit, Reason for amendment, Supporting evidence/reference where applicable, User ID/email, Date/time, Rule Engine version and Result of the re-evaluation. | The complete picture is already recorded across the Application History. The Edit Information step captures the old and new employer name with the previous source and the old and new classification, with user and timestamps; the financial effects are then recorded by the existing system steps of the same run — recalculation, Rule Engine execution and result, and Limit Assignment with the recalculated limit (BRD section 3, screen SC6). The Rule Engine itself maintains version control of the published strategies, so the version evaluated is traceable. Duplicating the financial values inside one consolidated step is a presentation preference rather than a control gap; we recommend keeping the established step model that the whole platform audit follows. | No change | Already covered across the history steps — BRD v1.0 section 3 action 6 + system steps, SC6. Reason/evidence fields follow the item 3 outcome. |
| 13. Atomic processing / rollback — All employer-related changes must be processed as one atomic transaction. The Employer Name should not be successfully updated while the classification, limit assignment or Rule Engine remains on the previous value. If any part of the recalculation or integration fails, the system should either Roll back completely to the last successful state; or Hold the application in a controlled pending/error status for recovery. Partial updates should not be permitted. | This reflects how the platform processes every queue edit today: the amendment and its downstream re-runs execute as one orchestrated flow while the application is locked against any other action, and the updated values are presented together on completion (BRD section 3). Transaction integrity and recovery behaviour are part of the platform's Day-1 processing architecture that all functions share — they are not introduced or altered by this feature. We will reflect the controlled-transaction statement in the BRD for clarity, with no change to scope. | No change | Platform processing model — BRD v1.0 section 3 action 7 (locking). v1.1 quotes the controlled-transaction statement for clarity only. |
