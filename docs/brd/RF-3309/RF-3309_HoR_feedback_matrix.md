# RF-3309 — Head of Retail feedback matrix v2 (original comments verbatim)

| Business requirement (original) | Appro feedback | Incorporated in BRD v1.1 | Note / description |
| --- | --- | --- | --- |
| 1. Employer selection and validation — The Employer Name should not operate as an unrestricted free-text field wherever this can be avoided. The preferred design should allow the Credit user to search and select the employer from the approved Employer Master / Empaneled Company List. If free text amendment is required as an exception, the system should require additional validation before the updated employer can affect ALOC, DBR, income multiplier, eligibility or limit. Please also define the employer matching logic, including Such as Exact match, Fuzzy match / confidence threshold., Arabic and English employer names, Trade name versus legal name, Employer aliases, Duplicate employer records, Active/inactive employer status. The BRD currently states that the updated name will be matched against the Empaneled Company List and the classification rerun. This needs to be more explicitly controlled | Accepted — Development. Search-and-select over the Empaneled Company List replaces the free-text field; free text remains only as a flagged exception. The matching logic he asks to control is the live platform logic the edit already re-uses (match against the Empaneled Company List at 0.9 confidence threshold, Category <> NON-ALOC, active status — classification is never taken from the typed text); it will be written out explicitly. Alias / Arabic coverage depends on Employer Master data quality (item 10). | Yes | BRD v1.1: section 2 redesigned (employer picker + exception free-text path, SC3 re-rendered); explicit matching-rules table added to section 3. The classification mechanics themselves: no change (BRD v1.0 section 3, system action 2). |
| 2. Source validation before applying the amendment — The employer amendment should follow a validation-first model. Where available, the amended employer should be validated against the relevant authoritative or supporting source, such as EFR / government employment record, salary information, employment certificate, pays lip or any other approved source used by the Bank. A manual amendment by the Credit user should not, by itself, be sufficient to establish a more favorable employer classification. | Already satisfied in substance — the design is validation-first: a manually typed name can never by itself establish ALOC; the classification results only from the independent system match against the approved Empaneled Company List (BRD v1.0 section 3, action 2; SC5 shows the re-classified result with match score). New: a supporting-evidence reference captured with the amendment; system-side EFR / document validation would be a new integration and is not proposed for this scope. | Yes | BRD v1.1: validation-first principle stated verbatim + evidence-reference field. Classification independence: no change (already v1.0). |
| 3. Mandatory reason for change — Every Employer Name amendment must require a mandatory reason code. Suggested reasons: Spelling correction, Employer legal name / trade name correction, Employer alias, EFR / government record mismatch, Employer Master mapping issue, Customer-provided information correction & Other. (If Other is selected, a mandatory comment should be required) | PUSH BACK. Consistent platform behaviour: none of the live Credit Queue Edit sections (Finalized Income, Liability Info, Length of Service, Other Income and Expenses) carries a reason field, and the amendment cannot of itself improve the classification (see item 2) — the control value of a reason code is limited while the full old-to-new trail, user and timestamp are already recorded in the Application History (BRD v1.0 section 3 action 6, SC6). A reason code adds friction to every correction without changing any system decision. | No — pushed back | No change to BRD. Fallback if insisted: reason dropdown is small development — can be added in v1.1 without redesign. |
| 4. STP versus exception handling — Please define a clear STP decision matrix. The expected design should be: STP: Employer successfully matched and validated, no conflicting information and no exception criteria triggered -> automatically update the employer, rerun classification, recalculation, Rule Engine and routing. Controlled STP: Employer is validated, but the amendment creates a material positive credit impact -> system performs the recalculation automatically but applies the relevant Credit approval level / delegated authority. Exception: Employer cannot be confidently matched, evidence conflicts, repeated amendments are detected, or other risk conditions are triggered -> application should move to manual review rather than allowing an unrestricted override. | NOT IN SCOPE of this feature. This feature delivers the capability to edit the Employer Name and re-run the existing logic (classification, recalculation, Rule Engine, routing) — which is exactly the STP leg he describes, already in BRD v1.0 sections 3 and 6. A Controlled-STP / Exception decision matrix with delegated-authority routing is a broader credit-workflow design to be discussed as a new scope, not inside this change. Note the edit already happens inside the manual Credit Queue, operated by authorised Credit users under the existing L1/L2/L3 authority model. | No — new scope | STP leg: no change (v1.0 flow diagram + sections 3, 6). Decision matrix / authority routing: separate scope discussion. |
| 5. Material positive credit impact — The system must identify whenever the employer amendment creates a more favorable credit position, including where it: Changes N-ALOC to ALOC. Moves the employer into a more favorable category. Increases permitted DBR. Increases income multiplier. Increases approved/proposed limit. Removes a deviation. Converts an otherwise ineligible application into an eligible application. These cases should be specifically controlled and visible to the approving Credit user. | NOT IN SCOPE of this feature — belongs to the same new-scope discussion as item 4. All seven values are already recalculated and displayed to the Credit user after the re-run (ALOC with match score, category, Rule Engine Result, Approve Limit Result — BRD v1.0 sections 3-4, SC5), and the before/after record is in the Application History (SC6). Automated favourable-delta detection with approval gating is new control logic for the new scope. | No — new scope | Visibility of recalculated results: no change (v1.0 SC5/SC6). Impact-detection control: new scope with item 4. |
| 6. Repeat employer amendments — The current BRD states that there is no cap on repeat edits. Please revise this requirement. Unlimited employer amendments are not recommended where the employer classification directly impacts DBR, multiplier and limit assignment. The system should have a configurable control over repeat amendments. At minimum, any subsequent amendment after the initial correction should trigger additional authority, reason capture and appropriate monitoring. | PUSH BACK. Repeat edits are already bounded and fully visible: every edit re-runs the Rule Engine under the existing shared re-run counter — more than 2 Rule Engine failures auto-rejects the application (BRD v1.0 section 3 action 4) — and every edit writes its own Edit Information step with the full old-to-new trail (SC6). The edit is performed by authorised Credit users inside the controlled queue; additional authority for repeats belongs to the item 4 new-scope discussion if pursued. | No — pushed back | No change to BRD (v1.0 already documents counter + per-edit audit). Fallback: configurable repeat threshold is feasible if the bank insists. |
| 7. Rule Engine rerun counter — Please ensure that: Technical/integration failures do not consume the business rerun counter. Only genuine business-rule failures are counted where appropriate. The customer is not rejected because of a system timeout, API failure or technical retry. | Agreed — this is already the behaviour: the counter counts business Rule Engine failures of the application (existing platform rule, unchanged by this feature); technical/integration failures follow error handling and never consume the counter or reject the customer. One clarification sentence added so it is explicit. | No change | BRD v1.0 section 3 action 4 (existing shared counter); v1.1 adds one clarification sentence only. |
| 8. AML / KYC impact — The BRD currently states that AML screening will not be rerun following an employer amendment. Please reconfirm this treatment with Compliance and clearly document the agreed logic. If employer information forms part of customer risk assessment, KYC profiling or screening, the appropriate refresh/reassessment should be triggered. | The treatment is documented in BRD v1.0 section 5: no re-screening on the edit — consistent with every existing Edit section — and the corrected name reaches the screening system through the post-decision CIF-update call. Confirmation to be obtained from Compliance; the documented logic stands unless Compliance directs otherwise. | No change | BRD v1.0 section 5 (EastNets row). Action: Compliance confirmation — owner Compliance; v1.1 adds a 'confirmed by Compliance on [date]' placeholder only. |
| 9. Fraud monitoring — Please include employer amendments in the fraud/control monitoring framework. At minimum, the system should make available for monitoring Number of employer amendments per application, Amendments by Credit user, N-ALOC to ALOC changes, Employer-category upgrades, Resulting limit increases, Repeated amendment to the same employers, Unusual concentration of amendments by a particular user. | PUSH BACK on new framework scope. Every data point listed is already captured per edit in the audit trail / Application History (user, timestamps, old/new name and classification — BRD v1.0 section 3 action 6, SC6) and is extractable for monitoring from day one. A dedicated fraud-monitoring capability / dashboards is reporting scope to be planned with item 18, not part of this change. | No — new scope | Monitoring source data: no change (v1.0 audit trail). Monitoring reports: new scope with item 18. |
| 10. Employer Master governance — Please define the ownership and governance of the Employer Master / Empaneled Company List. This should cover Employer ID if available, Legal name, Trade name, Arabic/English names, Aliases, ALOC classification, Category, Industry/sector, Effective date and Active/inactive status. Maker-checker for employer-master changes. | Out of this feature — the Empaneled Company List is a bank-owned master that exists today with its own upload and maintenance process; its governance, data model and maker-checker are a separate change request. This feature consumes the master as-is and automatically inherits every improvement made to it. | No — separate CR | Referenced in BRD dependencies only. Alias/Arabic matching quality (item 1) depends on this stream. |
| 11. Source hierarchy — The BRD should clearly distinguish between Customer-declared Employer Name, Original system-derived Employer Name, Validated Employer Name and Credit-amended Employer Name. The original source should never be lost or overwritten. Please also define the source hierarchy so downstream users can clearly understand which employer information has been used for the final credit decision. | Already covered: the four values exist as distinct, never-overwritten data points — customer-declared (Customer Journey input, never modified), system-derived original (kept at first edit), finalized working value, credit-amended (Source = Credit Department with Updated By/On) — BRD v1.0 section 3 action 1 and section 4; visible in SC5 (Company Name Source row). The finalized value is the single value used for the credit decision (section 5). | No change | BRD v1.0 sections 3, 4, 5 + SC5. v1.1 adds only a one-glance hierarchy table naming the same values. |
| 12. Enhanced audit trail — Please expand it to capture at minimum Old Employer Name, New Employer Name, Old/new Employer ID, Old/new source, Old/new ALOC status/category, Old/new DBR, Old/new income multiplier, Old/new proposed/approved limit, Reason for amendment, Supporting evidence/reference where applicable, User ID/email, Date/time, Rule Engine version and Result of the re-evaluation. | Accepted — Development (small). Baseline already records old/new name, old source, old/new ALOC, user and timestamps on labelled lines (BRD v1.0 section 3 action 6, SC6). Extension adds employer ID, DBR, multiplier, limit, evidence reference, Rule Engine version and re-evaluation result — all values the re-run already produces. (Reason field follows the item 3 outcome.) | Yes | BRD v1.1: audit field list expanded; SC6 re-rendered. Base trail: no change (v1.0). |
| 13. Atomic processing / rollback — All employer-related changes must be processed as one atomic transaction. The Employer Name should not be successfully updated while the classification, limit assignment or Rule Engine remains on the previous value. If any part of the recalculation or integration fails, the system should either Roll back completely to the last successful state; or Hold the application in a controlled pending/error status for recovery. Partial updates should not be permitted. | Accepted — his highlighted transaction paragraph is adopted verbatim. Locking during the run already exists (BRD v1.0 section 3 action 7); v1.1 makes the one-controlled-transaction / no-partial-commit / rollback-or-recovery rule explicit. | Yes | BRD v1.1: atomic-transaction clause in section 3; recovery status defined with item 15. Locking: no change (v1.0 action 7). |
| 14. Concurrency and locking — Please strengthen this further by ensuring that: Two users cannot update the employer simultaneously, A stale screen/session cannot overwrite a more recent employer update and Proper version/concurrency validation exists before saving. | Already covered in principle: the application is locked during processing and a concurrent action gets 'The Application is in another request processing.' (BRD v1.0 section 3 action 7). v1.1 adds the stale-session / version-check wording. | No change | BRD v1.0 section 3 action 7; v1.1 adds one strengthening sentence (version validation before save). |
| 15. Failure handling and resiliency — Please add explicit handling for Employer-classification service failure, Rule Engine timeout, Integration/API timeout, Duplicate submission, Retry, Idempotency, Partial processing and Recovery/reconciliation. A technical failure should not leave the application in an inconsistent state. | Accepted — new non-functional section covering the listed failure modes, idempotency and recovery; pairs with items 7 and 13 (technical failures never consume the business counter; no partial state). | Yes | BRD v1.1: new 'Failure handling and resiliency' section; engineering to size. |
| 16. Downstream consistency — Please add an explicit requirement that all downstream systems and documents must consume the same finalized Employer Name and classification following a successful update. There should be no situation where one system shows the original employer while another uses the amended employer for credit decisioning. | Already covered — this is exactly BRD v1.0 section 5: every consumer (application views across all queues and enquiry, CAM, Affordability Assessment Form, document stack, core banking, screening) reads the single finalized value after the update. The explicit one-sentence requirement is added above the table. | No change | BRD v1.0 section 5 (downstream consumers table); v1.1 adds the one-sentence explicit requirement only. |
| 17. Customer-declared information — I agree with the current approach that the original Application Form should continue to retain what the customer originally submitted. However, internally the system should clearly distinguish between: Customer Declared Employer and Bank Validated Employer. The customer declaration should never be overwritten. | Agreed by Head of Retail — already the design: the Application Form stays the customer's OTP-time record and the Customer Journey input is never modified (BRD v1.0 sections 3 and 5); the Customer-Declared vs Bank-Validated distinction is carried by the source data points of item 11. | No change | BRD v1.0 sections 3, 5; v1.1 adopts the 'Customer Declared / Bank Validated' terminology in the item 11 table. |
| 18. MIS and management reporting — Please include appropriate MIS / reporting capability covering Employer amendments by user, Employer amendments by employer, Old/new classification, Limit uplift/downward movement, Percentage processed STP, Percentage routed to exceptions, Repeat amendments, Approval/rejection outcome & Reason codes. | PUSH BACK on scope. The reporting dataset is derivable from the enhanced audit trail (item 12) from day one; a dedicated MIS / report pack is reporting scope to be planned separately together with item 9 — not part of this change. STP/exception percentages additionally depend on the item 4 new-scope decision matrix. | No — new scope | Source dataset: covered by items 12 / v1.0 audit trail. Report delivery: separate reporting scope with item 9. |
| Explicit requirements (highlighted paragraphs) — Employer Name amendment shall follow a validation-first, exception-based model. Manual amendment shall not by itself establish employer eligibility or classification. The system shall independently validate the amended employer against approved Employer Master data [...] Where validation is successful and no exception criteria are triggered, processing shall continue STP. Where the amendment results in an unverified employer, ambiguous match, material positive credit impact, repeated amendment or conflicting source information, the application shall automatically route to the applicable control/approval queue.
