AMP-3730 · Kha · SoC + Liability Letter templates

  1. SoC ownership: AMP-3404 AC10 and its Part-4 table say the Schedule of Charges is "Retrieved from Bank"; this story has the channel generating it with our own amortization/APR math. Please align with Trang — one generator. If the bank sends the file, AC2.1 Sections B/D become render-only.
  2. IA1 doesn't match the approved B2B flow: B2B has no "Your Offers" list (3404 Part 3 — single offer straight to Offer Detail); Settlement is pre-submission (3694 AC6), not step 7 after Accept; and 3404 AC11 is Customer Declaration, not "Application Form & Contract Signing". Please regenerate IA1 from 3694 + 3404.
  3. Naming: "Liability Letter" already means the customer-uploaded letter from their current bank (3728 doc list / DOC007 / 3689 upload flow). Suggest renaming this generated document (e.g. Settlement Confirmation Letter) — the LIABILITY_LETTER document_type will collide in the doc engine and Application Enquiry.
  4. Data source: Section B keys on the pre-submission settlement toggles, but 3404 AC6 allows contract re-scoping at Offer Detail and AC6a switches to DC incl. credit cards. Generate from the final accepted selection (3404 AC7 payload).
  5. One settlement figure: Balance + Overdue here vs the DC pool × 1.05 and buyout 1% fee absorption elsewhere — the letter's Net Amount Credited must equal 3404 AC9 Review Summary. Point both at one calculation service.
  6. APR: the Section A formula is a flat approximation; CBUAE disclosure APR is reducing-balance. Please confirm with compliance before it's hardcoded.

AMP-3689 · Trang · Resume by notification / Upload Document

  1. Status ownership: "[Application Status] is received from the bank — Appro renders it" conflicts with the SSS model (AMP-2195), where the channel derives display status. Please confirm which statuses are bank-passthrough vs SSS-derived — today two vocabularies would ship.
  2. Document Status dictionary: this story sets per-doc statuses locally, the bank sends verification results, and the Ops queue has its own "Awaiting Customer Upload". One shared enum with one owner per transition, please.
  3. Passport applicants: AC1.5 signs the Security Cheque with the Emirates ID signature from eKYC — passport-journey customers (AMP-3710/3711) have none. Gate cheque-signing to EID journeys or define the alternative.
  4. Filing generated docs: AC1.6 groups don't cover the generated SoC / settlement letter / contract pack (3730 IA1). Please add the group mapping.
  5. Cheque amount validation (≤120%, CBUAE Art. 7) sits in the Ops queue — worth stating explicitly that CJ validates signature only, so it isn't built twice.

Kept as-is (good): Trigger A consuming 3728 AC4 keeps a single document-resolution engine.

AMP-3679 · Trang · PL flow from Refinancing website

  1. Trigger point: AC4 labels Choose Finance Type → T&C → KFS as the "post-submission sequence", but per 3404/3694 submission is held until the Loading screen — these are pre-submission, and this decides when channel/bank integrations fire. Please align AC4 and the Post-Submission Logic table to the held-submission model.
  2. Dangling references: steps 10 and 14 say "See Open Item 1 / Open Item 2" — the ticket has no Open Items section. Add it or resolve inline.
  3. Pre-check ordering: Eligibility Pre-check (step 4a) runs before AECB (step 7). Confirm it uses declared obligations only per 3694 AC1; if it needs AECB the ordering breaks.
  4. Variant intent: the refinancing entry is DC intent, but the B2B sequence starts at Choose Finance Type with all variants. Should the UTM carry a default variant (DC/Buyout)? Backend needs to know whether variant comes from UTM config or customer choice.
  5. Passport identity: passport applicants (3710/3711) have no AECB — the AECB-powered liabilities/settlement screens can't run. Exclude passport from this entry point or gate to Fresh.

AMP-3680 · Trang · Hide PII sent to bank

  4. AECB score only at pre-qual: confirm the masked payload still satisfies the banks' pre-qualification rules, which currently key on DBR/obligations.
