03 · Findings (severity order)

P1 F1 — Two scope rows have no Jira ticket; CR header is empty

"Migrate data from SCB v2 to SCB v3" and "Limit Assignment" carry no ticket, no ACs, no owner. The SCB row is a production customer-data migration — the single riskiest item in the release — existing only as one sentence. The CR's own Package Timeline, Release Tag, Change Type and Release Note fields are blank.

Fix: No PROD date until both rows have stories with ACs (migration needs: gap list, mapping rules, dry-run plan, rollback). Fill the CR header or the release cannot be communicated to the bank.

P1 F2 — ETL stories contradict each other on which product they serve

The CR row and AMP-3744's title say ETL is for the PL flow. But AMP-3754 and AMP-3755 both state "Applicable Product: Covered Card — ETB (Web and Mobile App)" and their flows hang off the Covered Card journey (EID dedupe per ADIB-7176). Meanwhile the B2B PL journey needs ETL for the salary-transfer opt-in (AMP-3717). Which product does Release 5's ETL actually serve — CC, PL, or both?

Fix: One explicit "Applicable Product" decision across 3744/3754/3755, and the 21-exclusion runtime check confirmed (or explicitly excluded) for the PL journey.

P1 F3 — AMP-3757 (generic Digital Signature) has an empty description

It is a named release item under Required Document Module, and the signature model is already ambiguous across the journey (T&C/KFS swipe-stamp vs drawn signature vs EFR + OTP on the cheque). Releasing "generic digital signature" with zero ACs guarantees three inconsistent implementations.

Fix: 3757 gets a description defining one evidence model per document class before it stays in scope; otherwise pull it from Release 5.

P1 F4 — Two failed-reason codes ship as TBD, and the registry reference is cross-project

AMP-3754 adds RIM Status and Firco Flag exclusions with reason code "TBD" in both AC2 and AC3 — a customer can be CANCELLED with no code. The story also says codes "must be registered in the ADIB Failed Reason Codes list" — this is the SMBP Bank Portal; pointing the registry at another project is how code collisions start (RES146/147/148/155 are new and unverified against any SMBP registry).

Fix: Assign the two codes, and name the canonical SMBP failed-reason registry in the story (not ADIB's).

P1 F5 — Hard-gate defaults contradict the DP engine while claiming alignment

AMP-3753 AC6 bakes in defaults G2 ≥ 2 providers, G3 ≥ 30% utilisation. The Distribution Portal DC engine (AMP-2215) uses G2 ≥ 3, G3 ≥ 70%. Yet 3753 IA3 states the config is "aligned to ensure consistency between portals" — that claim is false as written. A bank running both portals gets different DC eligibility per channel on day one.

Fix: Decide per gate: deliberate B2B loosening (then delete the alignment claim and record the rationale) or align to DP values. Do not ship the contradiction into PROD config.

P2 F6 — AMP-3728 smuggles a full post-approval operating model without stories

Titled "document mapping", it introduces: a Persona Match check (salary ≥ 15,000, AECB ≥ 711, <14× multiplier — hardcoded), a Disbursement Maker/Checker Queue, DAF generation, DMS upload, a Fund Holding API and Camunda STL reminders — none of which exist as SMBP stories, all anchored on FAB tickets (FABL-1000/2047/1859) from another project. That is a release's worth of scope hidden in one story's AC5.

Fix: Split AC5's queue/persona/DAF machinery into their own stories with SMBP-native ACs; make persona thresholds configurable; keep 3728 to document resolution only.

P2 F7 — AMP-3754 ends with its own unanswered design questions

The story body closes with open bullets: age exclusion threshold undefined, FCCM risk-rating exclusion values undefined, expired-EID handling undefined — three ETL fields loaded (3744) but never validated. Acceptable pre-clarification; not acceptable in a PROD manifest unanswered.

Fix: Answer the three in-body questions (or explicitly de-scope those fields) before Ready for Dev.

P2 F8 — 3744 vs 3755: two validators, opposite outcomes for bad data

AMP-3744 AC2: format mismatches are loaded as-is + email to support. AMP-3755 AC3/AC4: missing column or duplicate RIM → reject + rollback. The boundary between "load anyway" and "roll back" is implied, never stated as one decision table — dev will pick a line, and QA another.

Fix: One table: failure class → blocking? → rollback? → notify? owned by whichever story keeps the loader.

P2 F9 — G4 blocked-status default list needs a sanity pass

3753's default 17 blocked statuses include "U (Active Payments)" — blocking customers whose contracts are actively being paid would fail nearly every applicant — alongside debatable entries (A Arrangement, C Settlement, E Extended). The letter-to-meaning mapping looks partially wrong against the AECB status dictionary.

Fix: Verify the 17 codes against the AECB reference list with Credit before the default ships; "U" in particular.

P3 F10 — Hygiene

(a) 3753 section numbering drifts (AC6 titled "Section 4", AC7 titled "Section 5" but its body says "Section 4"). (b) 3754/3755 base their preconditions on ADIB tickets (ADIB-7148/7149/7176) rather than restating rules — replication by reference is how cross-bank drift starts. (c) 3744's claim "replicate the same as ADIB" is unverified against ADIB-7148's field list — inference, not checked field-by-field. (d) AMP-3722 (UI feedback) is cosmetic scope inside a PROD CR with no description.
